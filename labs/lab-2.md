# Лабораторная работа 2

## Отрабатываемый материал

- Hibernate / JPA
- JDBC
- работа с PostgreSQL
- модульное разделение слоёв (Controller–Service–DAO)
- unit‑тестирование бизнес‑логики

## Предметная область

Разрабатывается **банковская система**, в которой:

- есть пользователи (логин, имя, возраст, пол, цвет волос, список друзей);
- у пользователей есть счета (идентификатор, баланс, владелец, история операций);
- поддерживаются операции пополнения, снятия средств и переводы между счетами с различными комиссиями.

Все данные должны храниться в базе данных, а доступ к ним — осуществляться через слой, реализованный с использованием ORM.

## Архитектурные требования

- **Слой доступа к данным (Data Access)** должен быть выделен в отдельный модуль проекта.
- **Слой сервисов (Services)** должен быть оформлен как другой модуль.
- Доступ к данным реализуется с использованием **PostgreSQL** и **Hibernate / JPA**.
- Сервисный слой инкапсулирует бизнес‑логику (расчёт комиссий, проверки баланса, ведение истории операций и т.п.).

Разрешается переносить или перерабатывать сущности в общий модуль моделей, если это упрощает использование ORM.

## Сосуществование с другими реализациями

Если в том же репозитории уже есть реализация банковской системы с in‑memory‑хранилищем:

- **не удаляйте** существующий код;
- организуйте проект так, чтобы старая реализация **не участвовала** в сборке и запуске варианта для данной лабораторной работы:
  - вынесите старые реализации DAO в отдельный модуль, не подключённый к модулю с точкой входа текущего приложения;
  - либо отключите их на уровне конфигурации сборки, исключив из зависимостей запускаемого модуля;
- убедитесь, что точка входа приложения использует только слой Data Access на Hibernate.

Важно: при запуске приложения и тестов **не должно быть конкуренции** между разными реализациями доступа к данным (никаких случайных обращений к in‑memory‑репозиториям).

## Функциональные требования

1. Вся информация о пользователях, счетах и операциях хранится в **БД PostgreSQL**.
2. Для связи с БД используется **Hibernate / JPA** (никаких самописных JDBC‑обёрток вместо ORM).
3. Должны быть реализованы:
   - создание пользователя;
   - просмотр пользователя;
   - управление списком друзей пользователя;
   - создание счёта (у одного пользователя может быть несколько счетов);
   - просмотр баланса счёта;
   - снятие средств со счёта;
   - пополнение счёта;
   - перевод средств между счетами с учётом комиссий:
     - между своими счетами — 0%;
     - другу — 3%;
     - остальным — 10%.
4. Все изменения баланса должны сохраняться в истории операций счёта.

## Нефункциональные требования

- Использовать **PostgreSQL** как СУБД.
- Все параметры подключения к БД (URL, логин, пароль, диалект и т.п.) должны храниться в ресурсах модуля Data Access.
- Запрещено использование Spring Framework и Spring Boot.
- Запрещено использование любых ORM, кроме Hibernate / JPA.
- Код должен быть разбит на модули как минимум:
  - модуль с моделями и/или общими сущностями (опционально);
  - модуль Data Access (Hibernate / JPA + JDBC, если необходимо);
  - модуль сервисов (бизнес‑логика);
  - модуль с точкой входа приложения и консольным интерфейсом.
- Бизнес‑логика должна быть покрыта **unit‑тестами**, которые не зависят от конкретной реализации репозиториев (используйте моки).

## Test cases

Тесты должны проверять **бизнес‑логику**, а не работу с конкретной БД или консолью. В тестах необходимо замещать реальный слой доступа к данным моками (или тестовыми double‑объектами).

Обязательные сценарии:

- **Снятие денег со счёта**
  - при достаточном балансе сохраняется счёт с корректно обновлённым балансом и историей операций;
  - при недостаточном балансе сервис возвращает предметную ошибку.
- **Пополнение счёта**
  - корректно обновляется баланс и история операций.
- **Переводы между счетами**
  - корректный расчёт комиссий для:
    - перевода между своими счетами;
    - перевода другу;
    - перевода остальным пользователям;
  - проверка, что после перевода сохраняются обе стороны операции (списание и зачисление) и история.

Тесты не должны зависеть от конкретного механизма хранения (PostgreSQL / Hibernate / JDBC). Всё, что относится к настройке сборки, CI, конфигурации Gradle/Maven, настройке среды, оформляется в отдельном файле **с примечаниями ко второй лабораторной**.
