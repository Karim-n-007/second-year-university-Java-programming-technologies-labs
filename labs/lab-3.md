# Лабораторная работа №3

## Отрабатываемый материал
Spring Framework, Spring Boot, JpaRepository, REST API, Dependency Injection, Swagger/OpenAPI, разделение слоёв приложения, управление транзакциями, оптимизация запросов к БД

---

## Задание
К созданному в прошлой лабораторной сервису добавляется использование Spring Framework, Spring Boot, внедрения зависимостей (Dependency Injection).

Контроллеры должны предоставлять HTTP эндпоинты (REST API) для получения информации о конкретных пользователях и их счетах и для взаимодействия с пользователями и их счетами.

---

## Функциональные требования
- Все сценарии из предыдущей лабораторной должны быть реализованы через HTTP эндпоинты.
- Реализовать эндпоинты для:
    - получения аккаунтов по идентификатору пользователя;
    - получения друзей по идентификатору пользователя;
    - получения всех пользователей системы с фильтрацией по цвету волос и гендеру;
    - получения всех аккаунтов;
    - получения всех операций с фильтрацией по типу и идентификатору аккаунта.

---

## Нефункциональные требования

### Общие
- Использовать Dependency Injection.
- Строгое соблюдение REST спецификации для эндпоинтов.
- Запрещается использовать xml-конфигурации для бинов (только Java-based аннотации).
- Контроллеры не должны отдавать или принимать доменные сущности (см. раздел «Разделение слоёв»).

### Swagger

**Требования:**
- Swagger UI должен быть доступен по стандартному пути (например, `/swagger-ui.html` или `/swagger-ui/index.html`) при запущенном приложении.
- **Каждый эндпоинт** должен содержать:
    - краткое описание того, что он делает (аннотация `@Operation(summary = "...")`);
    - описание **всех возможных HTTP-кодов ответа** с пояснениями (аннотации `@ApiResponse`) - как минимум коды успеха (200/201) и ошибок (400, 404, 500 и т.д., где это применимо).
- DTO-классы, используемые в запросах и ответах, должны иметь описания полей (аннотация `@Schema`), чтобы в Swagger UI была видна структура данных с пояснениями.
- На защите необходимо **открыть Swagger UI в браузере** и продемонстрировать:
    - наличие всех эндпоинтов с описаниями;
    - корректность описания кодов ответа;
    - возможность отправить запрос прямо из Swagger UI и получить ответ (функция «Try it out»).

### Разделение слоёв и моделей данных
В приложении должно быть **чёткое разделение** между моделями разных слоёв:

- **Entity-классы** (JPA-сущности) - классы, аннотированные `@Entity`, которые описывают структуру таблиц в базе данных и используются исключительно для взаимодействия с БД через JPA репоизтории. Эти классы живут на уровне слоя данных (persistence layer) и не должны «просачиваться» в вышележащие слои.
- **Доменные модели** (domain/business models) - классы, которые описывают бизнес-логику приложения и используются на уровне сервисного слоя. Они не зависят от деталей хранения (не содержат JPA-аннотаций) и отражают бизнес-правила.
- **DTO (Data Transfer Objects)** - объекты, которые контроллеры принимают от клиента и возвращают клиенту. Они определяют контракт REST API и не должны совпадать ни с Entity-классами, ни с доменными моделями.

Для преобразования между этими слоями необходимо реализовать **маппинг** (вручную или с использованием библиотек, например MapStruct). Цепочка преобразований должна выглядеть так:

```
Controller (DTO) - Service (Domain Model) - Repository (Entity)
```

> **Почему это важно:** если использовать один и тот же класс и для маппинга на таблицу, и для отдачи через REST, то при изменении схемы БД сломается API (и наоборот). Разделение моделей делает слои независимыми друг от друга, упрощает поддержку и тестирование.

### Проблема N+1 запросов
При реализации эндпоинтов, которые возвращают сущности со связями (например, пользователь и его аккаунты, пользователь и его друзья), необходимо **не допускать проблему N+1 запросов**.

Проблема N+1 возникает, когда ORM для получения коллекции из N родительских сущностей делает 1 запрос, а затем для каждой из N сущностей выполняет ещё по одному запросу для подгрузки связанных данных - итого N+1 запросов вместо одного-двух.

**Требования:**
- Во всех эндпоинтах, где загружаются связанные сущности, проблема N+1 должна быть устранена (например, с помощью `JOIN FETCH` в JPQL-запросах, `@EntityGraph` или `@BatchSize`).
- На защите необходимо **продемонстрировать**, что проблема N+1 решена: включить логирование SQL-запросов (`spring.jpa.show-sql=true` или через настройки Hibernate) и показать, что при запросе списка сущностей со связями выполняется оптимальное количество запросов к БД.

### Управление транзакциями
В местах, где выполняется несколько операций с базой данных, которые должны быть выполнены атомарно (либо все успешно, либо ни одна), необходимо использовать **декларативное управление транзакциями** через аннотацию `@Transactional`.

**Требования:**
- Операции, которые включают несколько изменений в БД в рамках одного бизнес-действия (например: создание пользователя вместе с аккаунтом, перевод средств между счетами, добавление друга с обновлением обоих пользователей), должны быть обёрнуты в транзакцию.
- Аннотация `@Transactional` должна располагаться на уровне **сервисного слоя**, а не на контроллерах или репозиториях.
- Для операций, которые только читают данные, рекомендуется использовать `@Transactional(readOnly = true)`.
- На защите необходимо **объяснить**, в каких методах и почему используются транзакции, и что произойдёт, если транзакцию убрать (например, частичное сохранение данных при ошибке).
